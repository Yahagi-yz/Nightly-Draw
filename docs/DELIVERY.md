# 定时与主动交付

## 用户指定的语义

每天 `22:00 Asia/Shanghai` 主动交付当次完整卡片，不要求用户先点击或回复。北京时间优先于设备/账号时区；不因当前设备位于其他时区而改成当地 22:00。

固定 UTC 调度表达为 `0 14 * * *`。这只是换算示例，不是已经部署的计划。

## 当前状态

`config/schedule.json` 中保存的是期望配置。`enabled=false`、`task_id=null`、`provider_status=not_created`。截至本次核查，没有为本项目创建或验证真实调度器。仓库已建立，但这没有改变推送状态；阻塞跟踪见 Issue #1。

## ChatGPT 路径

任务指令在 `prompts/chatgpt-nightly-task.txt`。须在实际支持 Scheduled 的入口创建并获得确认。官方帮助说明：任务功能受账号、应用及版本影响；项目中创建的任务不能直接访问该项目的上传文件。因此任务指令必须自包含，不能只写“按项目文件执行”。

已连接应用能否用于定时任务、是否需要授权、能否获取历史卡片和生成图片，都须在目标任务环境实测。不能假定 GitHub 文件每晚自动进入任务上下文。

如图片能力不可用，改发文字卡，不发提示词冒充图片。无法联网核验时优先使用可访问的已审核内容；若连可靠内容也不可获得，报告当次失败，不编造来源。

## 未来 App 路径（候选，未选定）

内容审核库 → 每日选卡 → 发布记录 → 已授权推送服务 → 客户端展示/回执。

把“选卡成功”“已发布”“发送服务接受”“客户端收到”“用户阅读”分开记录。网络超时未必表示未发送，重试前核对幂等记录。`用户或订阅标识 + Asia/Shanghai日期` 作为每日幂等键。

卡池不足时必须显式处理：补充审核内容、标注为重访，或报告缺卡；不能悄悄重复并谎称新卡。现有三个示例不构成日更保障。

推送渠道、服务提供方和费用仍待决定。本包不包含 GitHub Actions 定时推送，不用 GitHub Issue 通知或日历提醒偷换用户所说的内容推送。

## 开启成功的证据

服务返回任务 ID、启用状态、时区及下一次运行时间；做一次真实测试发送，保留不含敏感信息的结果；首次到点后核对执行记录与设备接收情况。没有上述证据不得写“已自动推送”。
